# EventHub — исходные материалы для зачёта

МДК 01.11 «Технология доступа к базам данных ADO.NET», группа 9/3-РПО-24/1.

## Состав
- `eventhub.sql` — создание SQL Server базы `eventhub`, шести таблиц, ограничений, индексов, тестовых мероприятий, сеансов, покупателей и связанных бронирований/билетов.
- `checks.sql` — запросы проверки целостности и доступности мест; **не** является готовым решением проекта.

## Установка
1. Откройте **SQL Server Management Studio (SSMS)** и подключитесь к Microsoft SQL Server 2022/2025.
2. Откройте `eventhub.sql` (кодировка UTF-8). Выполните скрипт целиком (F5).
3. Проверьте появление базы `eventhub` и шести таблиц: `events`, `venues`, `sessions`, `customers`, `bookings`, `tickets`.
4. Выполните `checks.sql` для проверки начальных данных.
5. В C#-проекте используйте пакет `Microsoft.Data.SqlClient`. Настройте строку подключения для **своего** сервера и базы `eventhub`.

**Важно:** скрипт **не перезаписывает** существующую базу. Если `eventhub` уже создана, он остановится с сообщением об ошибке. Не удаляйте чужие/рабочие базы. Для повторной установки преподаватель должен вручную удалить только старую учебную базу после резервного копирования.

## Сущности
| Таблица | Важные поля |
|---|---|
| `events` | `id`, `name`, `description`, `category`, `status` |
| `venues` | `id`, `name`, `address`, `capacity` |
| `sessions` | `id`, `event_id`, `venue_id`, `starts_at`, `price`, `status` |
| `customers` | `id`, `full_name`, `phone`, `email` |
| `bookings` | `id`, `customer_id`, `session_id`, `quantity`, `unit_price`, `status`, `created_at` |
| `tickets` | `id`, `booking_id`, `ticket_code`, `status` |

## Допустимые статусы
- `events.status`: `draft`, `published`, `cancelled`.
- `sessions.status`: `scheduled`, `cancelled`, `finished`.
- `bookings.status`: `confirmed`, `cancelled`.
- `tickets.status`: `valid`, `cancelled`, `used`.

Билет принадлежит бронированию; **одна бронь создаёт ровно `quantity` билетов**. При отмене все связанные билеты получают `cancelled`. Цена в `bookings.unit_price` хранит снимок цены билета на момент оформления (из `sessions.price`). Выручка по действующим бронированиям: `SUM(quantity * unit_price)` при статусе `confirmed`.

**Вместимость относится к каждому отдельному сеансу**, а не ко всему мероприятию. Действующее количество мест считайте по `bookings.status = 'confirmed'`, а не по всем броням, включая отменённые. Проверка мест и запись брони должны проходить в одной транзакции с подходящей синхронизацией конкурентных запросов. Например, сериализовать оформление брони для одного сеанса с использованием `UPDLOCK, HOLDLOCK` на строке сеанса и последовательно проверять количество действующих броней.

Стандартные внешние ключи и CHECK-ограничения **не предотвращают сами по себе перепродажу мест или несоответствие количества билетов**: это часть проверяемой логики приложения. В тестовых данных есть отменённые брони и статусы отменённого/завершённого сеанса для проверки отказов.

## Тестовые проверки
- Поиск события по части названия.
- Список сеансов и площадок.
- Попытка оформить бронь на `cancelled` или `finished` сеанс — отказ.
- Попытка брони для `draft` или `cancelled` мероприятия — отказ.
- Попытка забронировать больше свободных мест — отказ.
- Ошибка при выпуске билетов — транзакция должна откатить бронь.
- Повторная отмена — не должна менять данные.
